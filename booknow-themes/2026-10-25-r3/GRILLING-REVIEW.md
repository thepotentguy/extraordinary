## Q3 — Do the tests catch the real alignment failure and Clifftop lessons?

The initial `alignment.cjs` run failed on the exact complaint: at 1440, search was x90–1350, intro x78–1338, hero x90–1352. At 1024 it reproduced x24–1000 versus x12–988 and x24–1002. The regression compares intended sibling left AND right edges within 1px; page overflow alone is insufficient. Final extracted-ZIP results align at all five widths. Desktop date/occupancy/promo group tops are equal; CTA has an explicit second row. See `private-evidence/alignment-before.json` and `alignment-after.json`.

The expanded authored matrix covers home, results, rates, no availability, terms, photos, location and guest/consent at 320/390/768/1024/1440. Phone viewports use 320×740 and 390×844. Assertions include visible controls, target bounds, heading/policy/consent clipping, page containment, dialog containment and native-hidden card-field preservation. Functional checks exercise alternative dates, Back/Close, consent pointer/Space toggling and reduced-motion CSS.

The original-runtime lane additionally found a Hamiltons caption layer intercepting all three home image controls at desktop widths. The fix gives caption and control groups separate space; it does not force clicks or disable caption pointer events. `home-hit-before.json` preserves the failure, while final hit checks and native mouse runs verify the correction.

Map coverage is only the real CSS container around a clearly labelled placeholder. No Google Maps initialization or map API behavior is passed. Guest/consent content is synthetic and disconnected; actual native checkout validation, guest data, gateway, payment and confirmation remain absent.

## Q4 — Are navigation controls understandable, contrasted, touch-sized and keyboard usable?

Visual/touch claims pass locally: normal targets range from 44–56px high/wide, standard chevrons and Pause/Play are retained, and normal icon/background contrast ranges from 6.64:1 to 12.28:1 from actual CSS values. `previews/control-states.png` shows normal, hover, focus-visible and pointer-pressed styling. There is no invented disabled image-control state; native Play/Pause state changes are exercised. State proof is not a full accessibility audit.

**Native keyboard usability does not pass as a completed repair.** The original runtime generates IMG elements with title attributes and mouse handlers, without demonstrated button role or tabindex. CSS focus rules are shipped, but CSS cannot make those IMG controls keyboard-operable. Focus-visible screenshots use the explicitly keyboard-enabled authored fixture. They prove the CSS treatment, not native keyboard semantics. Runtime/vendor support is required; this remains an installation/accessibility acceptance item, not a hidden exception.

## Q5 — Is native IMG behavior separate from authored keyboard behavior?

Yes. `native-gallery.html` is a local-only original-runtime lane using the existing jquery/simpleGallery/createCarousel scripts and unmodified IMG controls. `source/native-gallery-check.cjs` exercises native mouse Pause/Next/Prev and hit testing separately on home and dialog across the width matrix. Native attributes, interception, target bounds and mouse outcomes are recorded in `private-evidence/native-gallery-checks.json`.

The authored journey fixture has separate local handlers/keyboard semantics. Its consent, recovery and Close tests do not certify the eRes/GWT application. Neither runtime lane contains a live booking system or new installed JavaScript.

## Q6 — Does the alignment fix persist from the actual final ZIP?

Yes. The build extracts the rebuilt archives before local tests. Hash checks cover the source/archive/served CSS. The Imbali regression then measures the extracted-asset preview, including sibling edges; the main matrix measures other screen widths/containers and the native runtime lane tests hit bounds. The per-member manifest, final SHA-256 and Git commit identify the candidate. Rebuilding with the documented Python/zlib versions reproduces the ZIP bytes.

## Q7 — What is ready, inherited, blocked or still needed?

Local visual/package and scoped fixture checks are delivery evidence. Sponsor/independent review is still pending. Production installation is not recommended on that evidence alone.

- **Fixed in R3:** Imbali's 12px intro offset and 2px hero overshoot; desktop booking stair-step; inconsistent image-target styling between home/dialog; Hamiltons caption click interception; preview rescue-style leakage.
- **Inherited/runtime follow-up:** native image keyboard semantics and JS carousel reduced-motion/autoplay behavior; native map initialization; native accessible names elsewhere.
- **Required installer gate:** property-specific authority and sponsor design acceptance; actual current-property backup/rollback verification; theme import and ordinary public CSS hashes; native desktop/mobile search, recovery, rates, terms, gallery, map and permitted guest/consent regression.
- **Absent coverage:** physical devices, soft keyboards, screen-reader task testing, native GWT dialog lifecycle/escape/focus trap, native policy/availability correctness, gateway/payment/confirmation, and end-to-end conversion/business benefit.

These gaps block an unconditional accessible/end-to-end UX-ready or production-release recommendation. They do not invalidate the scoped visual/package corrections. No installation, CMS edit, availability query, booking, hold, payment, paid tool or extra agent was used.
